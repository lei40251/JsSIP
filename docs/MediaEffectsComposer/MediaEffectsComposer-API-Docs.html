Overview

它不是"纯混音器"，而是一条媒体编排管线

MediaEffectsComposer 的核心职责是把多路 MediaStream / HTMLVideoElement 编排成一个统一输出流。它不仅负责把视频画到一张画布上，还负责源注册、布局计算、音频子混音、输出流导出、水印、源级镜像，以及 AI 虚拟背景。

如果你是为了读源码，这个模块应该从 lib/MediaEffectsComposer/MediaEffectsComposer.js 往下看；如果你是为了接 SDK，用法上要先分清 独立实例用法 和 RTCSession 内部接管用法。

输入 支持 MediaStream、HTMLVideoElement、以及批量源列表。
输出 支持 video / audio / mixed 三类输出，还支持子混音。
渲染 auto 创建期按 worker-webgl2 → main-webgl2 → main-2d 尝试；运行期降级链为 worker-webgl2 → main-webgl2 → worker-2d → main-2d。

快速上手

如果你的目标是快速接入，先看这一节；如果你的目标是读懂源码，不要急着往下扫 API，先看下面的"学习路线"。

1. 独立创建一个 composer

const MediaEffectsComposer = require('./lib/MediaEffectsComposer');

const composer = new MediaEffectsComposer([localStream, remoteStream], {
  width: 1280,
  height: 720,
  fps: 15,
  renderMode: 'auto',
  mirror: false,
  sourceMirror: false,
  watermarks: [
    {
      target: 'output',
      type: 'text',
      text: 'CRTC Demo',
      position: 'bottom-right',
      fontSize: 28,
      color: '#ffffff',
      backgroundColor: 'rgba(0,0,0,0.45)'
    }
  ]
});

const mixedStream = await composer.getOutput({ type: 'mixed' });
优先记住：getOutput({ type: 'video' }) 只拿视频，mixed 才是音视频一起返回。

2. 运行时更新配置

await composer.setConfig({
  outputMirror: true,
  mirrorWatermarksWithOutput: true,
  sourceMirrorOverrides: {
    0: true,
    1: false
  }
});

await composer.setWatermarks({
  target: 'output',
  type: 'image',
  image: 'https://example.com/logo.png',
  position: 'top-right',
  width: 96,
  height: 96
});
适合热更新的内容主要是镜像、水印、源级 AiVB。输出宽高和渲染模式本质上是构造期主参数，文档上不要把它理解成"随便热切换"。

RTCSession 集成路径

这一节建议在看完"学习路线"第 1 个问题后再读。它解决的是：这个模块在会话里到底承担哪一段职责。

这个模块不仅能单独用，也会被 RTCSession 通过 MediaPipeline 自动调用。集成路径在 lib/RTCSession/MediaPipeline.js。

会话内的调用链

getUserMedia 原始流 → processMediaStream() → applyAiNoiseSuppressionOnSdkGumStream() → applyMediaEffectsComposerOnSdkGumStream() → 最终发送流
集成行为： 在 RTCSession 这条链路里，当输入流有音频轨时使用 getOutput({ type: 'mixed' }) 获取 composer 的完整音视频输出；当输入流无音频轨时使用 getOutput({ type: 'video' }) 仅取视频输出。
也就是 applyMediaEffectsComposerOnSdkGumStream() 会根据输入流是否含音轨来自动选择输出类型，composer 自身的混音输出直接被纳入最终发送流。 
const composerOutputStream = await composer.getOutput({
  type : hasSourceAudio ? 'mixed' : 'video'
});
const mixedVideoTrack = composerOutputStream.getVideoTracks()[0];

const mixedStream = new MediaStream();
composerOutputStream.getAudioTracks().forEach((track) => mixedStream.addTrack(track));
mixedStream.addTrack(mixedVideoTrack);

所以如果你是在会话里配 mediaEffectsComposer，应该把它理解成：

  • 视频层：合成、多路布局、镜像、水印、AiVB。
  • 音频层：当使用 type:'mixed' 时，composer 自身的音频混音结果会被纳入输出流。

主控层

  • MediaEffectsComposer.js：公开 API、模块编排。
  • ComposerConfig.js：构造参数归一化。
  • Sources.js：每一路 source 的生命周期。

执行层

  • LayoutEngine.js：计算每路源的展示区域。
  • RenderLoop.js：rAF 驱动、重绘、降级。
  • OutputStream.js：把 canvas 导出成真实流。

效果层

  • Watermark.js：水印规范化、资源预加载。
  • AiVBState.js：源级虚拟背景和 runtime 状态。
  • AudioMixer.js：音频混流和子混音。

生命周期与运行机制

这一节的重点不是背调用名，而是把"构造期"和"运行期"分开。很多误解都来自把这两类行为混在一起。

构造阶段

  • 参数归一化，生成内部 _config。
  • 创建 canvas、源注册表、音频模块、输出模块、布局模块、渲染循环。
  • 预加载初始水印。
  • 调用 addSource(videos, ...) 把初始源接入；appendStream() 只是兼容别名。

出流阶段

  • getVideoStream() 会确保首帧可绘制并启动输出视频流。
  • getAudioStream() 会懒初始化 AudioContext。
  • getMixedStream() 本质是先拿视频，再把音频轨补进混合流。

停止阶段

  • 打上 _destroyed 标记。
  • 停止渲染循环并清空所有源。
  • 停止音频合成、AiVB 状态、输出流和 capture tracks。
实例不可复用： stop() 之后，主类会拒绝再次调用大部分公开方法。源码里用 _assertNotDestroyed() 保护，报错文案会明确提示"Create a new composer"。

渲染路径

读这一节时，建议你同时打开 RenderLoop.js 和 RenderLoop.js。前者决定"先选谁"，后者决定"出问题了怎么退"。

渲染器选择逻辑主要在 lib/MediaEffectsComposer/RenderLoop.js，而运行时故障后的降级逻辑主要在 lib/MediaEffectsComposer/RenderLoop.js。

renderMode: 'auto' 的真实策略

创建期（同步）: → worker-webgl2 → main-webgl2 → main-2d（绝对兜底） 运行期降级（异步，仅 Worker 故障时触发）: → main-webgl2 → worker-2d → main-2d

为什么会强制主线程或 main-2d

  • 源级 AiVB / 特定镜像策略可能要求主线程 renderer。
  • 如果 Worker 后端初始化失败，代码会继续尝试主线程路径。
  • 明确指定 main-2d 时，不会再尝试更激进的渲染后端。

怎么观察当前实际渲染器

const info = composer.getRenderInfo();

console.log(info.actualMode);
// worker-webgl2 | main-webgl2 | worker-2d | main-2d | worker-init | worker-failed | not-started

getRenderInfo() 适合做 demo 面板和线上排障，不建议把它当业务逻辑分支条件。

主 API 参考

API 表适合查，不适合学。建议在已经理解主链路以后，再把这里当速查表使用。

参数速查

看参数时要分两类：一类是构造期决定主结构的，一类是运行时适合热更新的。不要把它们看成同一种配置。

你想做什么 优先看什么 原因
改输出分辨率 / 帧率 width / height / fps 这是构造期主参数，更适合重新创建实例。
切整体镜像 mirror / outputMirror 影响最终输出流。
切某一路源镜像 sourceMirror / sourceMirrorOverrides 这是源级或 slot 级策略。
加水印 watermarks 由 Watermark 做规范化和资源准备。
给某一路开虚拟背景 sources[].aiVirtualBackground AiVB 是 source 级能力，不是全局输出能力。

构造参数 MediaEffectsComposerOptions

字段 类型 说明
width / height number 输出画布宽高。默认分别为 1280 / 720。
fps number 输出帧率。ComposerConfig 默认归一化为 15；安卓微信 / 鸿蒙浏览器下默认 60。
backgroundColor string 画布底色，默认 #000。
audioGain number 全局默认音量增益，默认 0.8。
renderMode 'auto' | 'worker-webgl2' | 'main-webgl2' | 'worker-2d' | 'main-2d' 渲染后端选择。非法值会回退到 auto。
workerUrl string 可选外部 Worker 脚本地址。不传时通常走 Blob Worker。

maxFrameQueue number 保留的最大帧队列，当前默认 1。
preserveDrawingBuffer boolean 默认 true。
mirror boolean 最终输出整体镜像，内部字段名是 outputMirrorX。
sourceMirror boolean 所有源的默认镜像策略，内部字段名是 mirrorX。
mirrorWatermarksWithOutput boolean 当输出镜像时，输出级水印是否一起翻转。
watermarks Watermark | Watermark[] | null 初始水印列表。
sources SourceOptions[] | null 与初始输入源逐项对应的源级配置。

字段 说明

AiVB 配置重点

字段 说明

常见用法示例

下面的示例按"最常见学习场景"排序，不按接口完整性排序。你可以先抄最接近自己场景的例子，再回头对照 API 表。

const composer = new CRTC.MediaEffectsComposer([localStream, remoteStream], {

  renderMode: 'auto',
  sources: [
    {
      slot: 0,
      sourceMirror: true,

composer.addSource(remoteStream, { slot: 1 });

易错点

如果你一边看源码一边觉得"这里怎么跟我预期不一样"，优先先看这节，很多困惑其实是模块边界没建立起来。

1. 把 output mirror 和 preview mirror 混为一谈

setMirror() 改的是实际输出流，不是页面上 video { transform: scaleX(-1) } 这种本地预览样式。

2. RTCSession 集成的音频行为

会话集成路径里，当输入流有音频轨时使用 type:'mixed'（含 composer 混音输出），无音频轨时使用 type:'video'。这个行为在 MediaPipeline.applyMediaEffectsComposerOnSdkGumStream() 里写得很明确。

3. stop() 后继续复用实例

不支持。源码显式把实例标记为 destroyed，之后继续调用会抛错。

4. 以为所有配置都适合运行时切

镜像、水印、AiVB 很适合热更新；分辨率、渲染模式这类主结构参数更适合重新创建实例。

5. 忽略移动端宽高交换

RTCSession 集成里，buildMediaEffectsComposerCtorOptions() 在移动端默认会交换宽高，除非显式传 forceNoSwapWH: true。这个字段只用于 RTCSession 侧推导，不会继续传给 composer 构造参数。

6. 误用 AiVB 颜色字段

外部输入时常写 color，但内部状态快照里常看到的是 backgroundColor。这是归一化过程导致的，不是两个并存参数。
