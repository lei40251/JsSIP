Deep Dive

MediaEffectsComposer + AINoiseSuppression + RTCSession 深入说明

这份文档的目标不是“告诉你有哪些 API”，而是让你在读完以后，能真正理解 MediaEffectsComposer、AINoiseSuppression、 RTCSession / MediaPipeline 三者怎么配合、为什么这样设计、通话里什么时候重建、什么时候热更新、切设备时为什么这么处理。

Scope: MediaEffectsComposer Scope: AINoiseSuppression Scope: RTCSession Integration Demo: base-js Demo: media-effects-composer

主要依据的源码文件： lib/MediaEffectsComposer/*、 lib/AINoiseSuppression/*、 lib/RTCSession.js、 lib/RTCSession/MediaPipeline.js、 demo/base-js/js/app-media-effects.js、 demo/base-js/js/app.js、 samples/media-effects-composer/js/app-media-effects-composer.js。

说明方式上，我尽量做到“细到每个方法、每类状态、每段代码为什么存在”。 但因为这些模块内部 helper 非常多，文档里采用的是 按连续代码块解释 的方式： 如果 5~10 行都在做同一件事，我会按一个 block 解释，而不是机械地逐字符复述。 这样你更容易真的理解，而不是看一堆没有信息密度的“这一行声明变量，那一行赋值”的描述。

2. 总体架构

一句话结论：

当前产品边界下，MediaEffectsComposer 在 RTCSession 里承担的是 “会话启动时先服务单源，通话中允许扩展成多源” 的角色； AINoiseSuppression 则承担 “音频输入轨级别的 AI 处理器” 的角色。

RTCSession 自己不会保存 composer 实例里的全部动态状态。 它只缓存 source 0 的会话级配置 和 输出层配置，目的是为了能在重建采集链时恢复“本地主源的效果”， 而不是把 composer 当成一个完整多源房间状态机。 

RTCSession.connect()/answer()
  -> MediaPipeline.getUserMediaWithSessionPipeline()
     -> getUserMedia()
     -> processMediaStream()             // 外部注入预处理
     -> applyAiNoiseSuppressionOnSdkGumStream()
     -> applyMediaEffectsComposerOnSdkGumStream()
  -> 最终送入 RTCPeerConnection sender

运行中
  -> rtcSession.updateMediaEffectsComposer()
     -> 已有 composer: 走 setConfig() / setSourceMirror() / AiVB patch
     -> 没有 composer: 基于当前本地 track 或缓存输入流重建 composer

切设备
  -> switchDevice('camera')
     -> 如果当前会话正在使用 composer, 优先在同一个 composer 内 remove old source + add new source
  -> switchDevice('audio')
     -> 如果当前会话正在使用 AiNS, 优先复用现有 AiNS engine 做 replaceAudioTrack()

为什么要拆成两层

RTCSession 是会话状态机，负责 SIP / PeerConnection / sender 替轨。 MediaPipeline 是媒体加工编排器，负责把“采集、预处理、AiNS、Composer”串起来。 这样会话状态和媒体处理状态不会互相污染。

为什么 Composer 与 AiNS 分开

Composer 的重心是 视频输出合成，顺带管理混音； AiNS 的重心是 输入音轨处理。 两者生命周期不同，切麦克风和切摄像头的最优重用路径也不同，所以不应该绑成一个类。

3. MediaEffectsComposer 总览

你可以把 MediaEffectsComposer 看成一个“组合型运行时”。外部看起来是一个类， 但内部其实由 8 个主要子系统一起工作：

子系统 文件 职责 为什么单独拆出
Facade MediaEffectsComposer.js 兼容旧 API 名称，如 appendStream() 让旧 demo / 旧业务调用不需要整体迁移
Runtime Core MediaEffectsComposer.js 主控制器，组装所有子模块，暴露公共 API 把真正状态集中在一个地方，方便调试和复用
Config ComposerConfig.js 归一化构造参数和 source 参数 避免所有子模块都重复做类型校验
Source Registry Sources.js 管理输入源、slot、隐藏 video、source 快照 把“源对象”的生命周期从主类里拿出来
Layout LayoutEngine.js 计算每个 slot 在画布里的绘制区域 让渲染后端只专注“怎么画”，不关心“画到哪里”
Audio AudioMixer.js WebAudio 混音、子混音、换源重连 音频图比视频渲染复杂很多，独立后更清晰
Output OutputStream.js 管理 captureStream() / Insertable 输出 输出链和渲染链解耦，可以单独切换策略
Render Loop RenderLoop.js rAF 节奏控制、renderer 创建、降级 把“何时渲染”和“如何渲染”分开
Effects Watermark.js、aiVirtualBackground/* 水印、AiVB 的配置与运行时状态 效果本身会继续扩展，适合独立模块化

特别重要的边界：

在 RTCSession 里，composer 默认只会拿一条本地输入流做 source 0。 也就是说，会话建立时它天然是“单源效果处理器”。 但 composer 实例本身仍然支持 addSource() 扩展成多源。 这个扩展是 实例态，不是 RTCSession 缓存态。

  • source 不是“只有流”的薄对象，而是“媒体源运行时状态容器”。不这样做，AudioMixer / Layout / AiVB 都会到处维护平行 map。

  • slot 冲突直接覆盖，是为了保证“同一个 slot 表示同一个视觉位置”这个语义足够强。

这个文件只负责回答一个问题：每一帧里每一路应该画在哪里。 它不负责真正画图，所以所有 renderer 都能复用它的结果。

理解 createRenderPayload()

这段代码的逻辑顺序非常重要：

  1. 先 prepareCanvas() 和 resizeRenderer()，保证本帧输出尺寸已同步。
  2. 算出网格行列，再得到每个 cell 的宽高。
  3. 遍历 source：有视频就按视频画；没视频但有音频就给它一个占位画布；两者都没有就跳过。
  4. 把 outputMirrorX、mirrorWatermarksWithOutput、水印项一起放进 payload。

4.5 lib/MediaEffectsComposer/AudioMixer.js

这是 Composer 里最复杂的文件之一。它做的不只是“混一路音频”，而是：

  • 延迟创建默认 AudioContext。
  • 支持默认全量混音。
  • 支持按 slot 做子混音。
  • 支持 isolated 子混音，也就是独立 AudioContext 的子图。
  • 支持外部 video 换 srcObject 时自动断旧连新。
  • 支持源被覆盖 / 删除 / 轨道 ended 后的安全清理。

这个文件最值得理解的 4 个设计点

  1. 延迟创建 AudioContext： 如果调用方从来不请求音频输出，就不应该平白拉起 WebAudio。
  2. getStableAudioStream()： 为了让 getMixedStream() 返回的流在“先无音频、后补音频”场景下仍然稳定。
  3. refresh 串行化： 多路 add/remove、外部换源、track ended 可能同时发生，必须把 refresh 串成一条线。
  4. track signature： 不是看到 stream 引用变了就重建，而是比较“音频轨身份是否真的变了”，避免无意义重连。

4.6 lib/MediaEffectsComposer/OutputStream.js

这是“把 canvas 变成输出流”的模块。它现在有两条输出路径：

  • Insertable 路径： 用 VideoTrackGenerator / MediaStreamTrackGenerator 手动写 VideoFrame。
  • captureStream 路径： 用 canvas.captureStream() 直接取视频轨。

为什么需要单独的输出管理器

  • 渲染器只关心“画面已经画好了”。
  • 输出管理器关心“怎么把这张画面变成视频轨”。
  • 以后如果插入新的输出策略，比如更强的 Insertable 优化，不需要碰 layout / audio / source 管理。

为什么要有 latest-frame-wins

如果 Insertable 写帧速度跟不上渲染速度，最糟糕的做法是把所有帧都排队。 那样不会“掉帧”，但会越来越延迟。这里选择的是 只保留最新帧： 视觉上可能少几帧，但时延不会越堆越大，更适合实时通话。

为什么 RenderLoop 必须独立

  • “空 payload 是否需要真的起渲染器”这种性能策略放在 loop 层最合适。

4.8 lib/MediaEffectsComposer/MediaEffectsComposer.js

这是整个 composer 的主控制器，也是最值得读透的文件。

状态聚合与 getState()

状态分散在多个子模块中（Sources、RenderLoop、AudioMixer、OutputStream 等）。 MediaEffectsComposer.getState() 直接向各子模块收集数据并返回统一的只读快照， 内部通过 _collectRenderInfo、_collectAudioInfo、_getConfigStateSnapshot 等私有方法完成聚合，带有日志签名去重机制。

5. AINoiseSuppression 总览

AINoiseSuppression 的对外入口只有一个：AiNoiseSuppression。 但它内部是三层： 

AiNoiseSuppression
  -> AiNoiseSuppression
     -> AiNSWorkletRuntime
        -> AiNSWorkletSource (内联 worklet 代码, 里面跑 wasm + model)

这三层为什么必须分开：

  • Engine 面向业务层，负责“作为一个产品功能怎么用”。
  • Processor 面向媒体图，负责“如何把输入音轨接成输出音轨”。
  • WorkletRuntime 面向 DSP 运行时，负责“资源、模块、控制消息”。

7.4 会话级 composer cache 只缓存什么

mergeSessionMediaEffectsComposerOptions()（256-290）明确说明了缓存边界：

  • 缓存输出层配置，比如 mirror、watermarks。
  • 缓存 source 0 的配置，比如 sourceMirror、aiVirtualBackground。
  • 缓存重建 composer 需要的构造参数，比如 width/height/fps/renderMode。
  • 不缓存 你在运行中的 composer 实例上后来 addSource() 的那些动态多源状态。

这就是为什么：如果你在通话中把 composer 扩成了多源，后面发生重建时， RTCSession 不会自动帮你把这些额外 source 放回去。那部分属于业务自己的实例态，需要你自己重放。

原因很直接：这些字段本质上是 构造时决定 renderer / output / capture 路径的“硬配置”。 运行时改它们，要么需要重建 canvas capture，要么需要重建 renderer，要么会影响输出轨语义。 与其默默做高风险重建，不如显式拒绝，让调用方知道这不是一个轻量 patch。

在 RTCSession.connect()（586+）和 answer()（1088+）里，逻辑非常一致：

  • 从 options 里提取 mediaEffectsComposer。
  • 从 options 里提取 aiNoiseSuppression。
  • 缓存到 _sessionMediaEffectsComposerOptions 和 _sessionAiNSOptions。
  • 后续真正取流时，统一交给 MediaPipeline.getUserMediaWithSessionPipeline()。

示例位置： RTCSession.connect() 里见 598-604； RTCSession.answer() 里见 1104-1110。

7.11 switchDevice('camera')：为什么 composer 分支不直接重建整个会话

关键代码在 1866-2225。它的优化目标是： 如果当前通话已经在用 composer，尽量在同一个 composer 实例内替换 source 0。

代码范围 解释
1892-1896判断是否走 composer branch：必须有 session composer 配置、composer 实例、composer 输入流。
2040-2062封装统一 getProcessedStream：如果当前没有完整 composer 分支但 session 声明了 composer，就仍通过 MediaPipeline 取流。
2114-2125默认分支：停旧 sender.track，直接替换成新流的视频轨。
2130-2138composer 分支里，先停的是旧输入 videoTrack，不是 sender 上的合成输出轨。
2147-2159构造新的 composer 输入流：优先保留旧输入流里的音频轨，再拼上新 videoTrack。
2160-2189从当前 composer 读取 source 0 的 AiVB 和镜像状态，避免 remove/add 后丢效果。
2193-2196在同一个 composer 内 removeSource(oldInputStream) + addSource(newInputStream, sourceOptions)，并刷新 _mediaEffectsComposerInputStream。
2198-2208从当前 composer 再取一条新的视频输出轨，替换 sender。
2212-2224如果 composer 分支任何一步失败，回退到默认路径，优先保证切设备成功。

7.12 switchDevice('audio')：为什么优先复用 AiNS

关键代码在 2237-2302。逻辑是：

  1. 先停旧的 AiNS 输入音轨。
  2. 重新取新的麦克风流。
  3. 调用 replaceAudioTrackWithSessionAiNoiseSuppression(stream)。
  4. 替换 _localMediaStream 里的音轨。
  5. sender.replaceTrack(audioTrack)。

这样做的好处是：WASM 和 WorkletNode 尽量不重建，切麦克风更快，也更稳。

7.13 终止会话时如何清理

在 RTCSession._close() 一带（3795-3798），会显式调用： 

this._mediaPipeline.stopSessionMediaEffectsComposer();
this._mediaPipeline.stopSessionAiNoiseSuppression();
this._sessionMediaEffectsComposerOptions = null;
this._sessionAiNSOptions = null;

这保证了：

  • composer 内部的 renderer、AudioContext、captureStream 轨道被清掉。
  • AiNS 的 WorkletNode、WASM 运行时、AudioContext 被清掉。
  • 会话结束后不会把上一通的效果状态带到下一通。

9. 正确使用方式

9.1 直接用 Composer

const composer = new CRTC.MediaEffectsComposer([localStream], {
  width: 1280,
  height: 720,
  fps: 15,
  renderMode: 'auto',
  mirror: false,
  sources: [
    {
      slot: 0,
      sourceMirror: true,
      aiVirtualBackground: {
        mode: 'blur',
        assetConfig: { cdnUrl: './assets/aivb' }
      }
    }
  ]
});

const mixed = await composer.getOutput({ type: 'mixed' });

9.2 通过 RTCSession 使用

session.connect(target, {
  mediaConstraints: { audio: true, video: true },
  mediaEffectsComposer: buildCallComposerOptions(),
  aiNoiseSuppression: buildCallAiNsOptions()
});

这时请牢记：

  • mediaEffectsComposer 是会话级配置，不是完整多源实例状态快照。
  • aiNoiseSuppression 是会话级输入音轨处理配置。

9.3 通话中更新输出镜像 / 水印 / source 0 AiVB

await rtcSession.updateMediaEffectsComposer({
  mirror: true,
  watermarks: [ ... ],
  sources: [
    {
      sourceMirror: true,
      aiVirtualBackground: {
        mode: 'image',
        imageUrl: '/bg/office.png'
      }
    }
  ]
});

这类字段可以 patch。像 width、fps、renderMode 这种构造级字段不行。

9.4 通话中扩展成多源

const composer = rtcSession.getMediaEffectsComposer();
composer.addSource(remotePreviewStream, { slot: 1 });
composer.addSource(screenStream, { slot: 2 });

这会立刻在当前实例内生效，但这部分不是 RTCSession 的会话缓存态。后续如果会话链路重建，业务需要自己决定是否重放这些额外 source。

10. 常见坑

坑 为什么会踩 正确理解
以为 updateMediaEffectsComposer() 什么都能改 名字像全能 patch 它只支持运行时软配置；构造级字段会被拒绝。
以为 RTCSession 会记住所有动态 addSource() 看到 composer 支持多源 RTCSession 只缓存 source 0 和输出层配置，多源扩展是实例态。
切麦克风时重建整条 AiNS 链 不知道有 replace path 优先用 replaceAudioTrackWithSessionAiNoiseSuppression()。
切摄像头时直接 stop sender 上的 composer 输出轨 把“输入轨”和“输出轨”混了 composer 分支优先替换的是 composer 输入流里的原始 videoTrack。
source 有音频时仍想保留原音轨上行 按旧认知觉得 composer 只处理视频 当前逻辑已改成优先使用 composer 的 mixed audio，才能让音频混流/增益真正生效。
把 AiVB 内部状态挂回 source 做调试 旧实现容易这么写 现在状态属于 AiVBState._states 这个 WeakMap。

MediaEffectsComposer： 一个以视频合成为中心、顺带提供混音和效果控制的多子系统运行时。

AINoiseSuppression： 一个以输入音轨处理为中心、通过 Worklet + WASM 完成 AI 降噪的音频处理器。
