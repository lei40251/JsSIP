# RTCStatsMonitor 通话质量解读指南

本文面向普通接入方，说明 `demo/base-js/` 通话画面下方统计区域的含义，以及出现异常时应优先检查什么。

页面数据来自 `RTCSession` 转发的 `stats:detailed-report` 事件。接入方通常只需要消费这个摘要事件，不需要自行管理 `RTCStatsMonitor` 的启动和停止。

```js
session.on('stats:detailed-report', function(report)
{
  console.log(report.connection);
  console.log(report.outbound, report.inbound);
  console.log(report.quality);
});

session.on('stats:stats-error', function(error)
{
  // 统计失败不会中断通话，可按需上报或记录。
  console.warn(error.code, error.message);
});
```

> 浏览器提供的 WebRTC 统计字段并不完全一致。页面中的 `-` 表示浏览器未提供、尚未建立采样基线或当前无法计算，不等于数值为 0。

## 1. 建议判读顺序

1. 先确认“网络连接”中的状态、ICE 和 DTLS 是否已连接。
2. 再看 RTT、上下行网络质量和丢包。
3. 根据用户现象检查对应媒体流的码率、抖动、画面尺寸和 FPS。
4. 查看“存在问题”是否给出明确提示。
5. 最终以用户实际听感和观感为准，不要只根据单个数值下结论。

## 2. 上行链路

上行表示本端发送给远端的媒体，例如：

```text
音频[0] | 编码:opus | 码率:28.0kbps | 抖动:1.25ms | 丢包:0%
视频[1] | 编码:H264 | 码率:320.1kbps | 抖动:3.23ms | 丢包:0%
        | 画面:640x480 | FPS:17 | 编码:2.533ms | 限制:none
```

| 页面字段 | 含义 | 需要关注的表现 |
| --- | --- | --- |
| 音频/视频 `[MID]` | 当前发送的媒体及其 SDP MID；MID 用于区分多路媒体 | 业务应有该媒体，但对应行长期不出现 |
| 编码 | 实际协商使用的编解码器 | 与业务要求不符，或媒体已发送但长期为 `-` |
| 码率 | 最近一个采样周期的实际发送码率 | 持续说话或运动画面时长期接近 0，并伴随无声、模糊或卡顿 |
| 抖动 | 远端接收本端媒体时观测到的网络波动 | 持续升高，并伴随丢包或远端听感、观感变差 |
| 丢包 | 本端媒体到达远端前的丢失比例 | 持续大于 0，尤其伴随音频断续、马赛克或卡顿 |
| 画面 | 实际编码发送的视频尺寸 | 长期明显低于预期，并且用户看到画质下降 |
| FPS | 实际编码帧率 | 运动画面下持续偏低或降到 0 |
| 编码耗时 | 平均编码一帧所需时间 | 持续升高并伴随低 FPS、CPU 限制或卡顿 |
| 限制 | 浏览器报告的视频质量限制原因 | `bandwidth` 表示带宽受限；`cpu` 表示编码性能受限 |

静止画面、黑屏、静音或没有声音输入时，媒体码率降低可能是正常现象。判断码率是否异常时，应同时看画面内容、FPS、丢包、限制原因和远端实际体验。

## 3. 下行链路

下行表示本端从远端接收并解码的媒体。

| 页面字段 | 含义 | 需要关注的表现 |
| --- | --- | --- |
| 音频/视频 `[MID]` | 当前接收的媒体及其 SDP MID | 远端应发送该媒体，但对应行长期不出现 |
| 编码 | 本端实际接收的编解码器 | 与协商或业务要求不符 |
| 码率 | 最近一个采样周期的实际接收码率 | 远端正在发送，但码率长期接近 0 |
| 抖动 | RTP 包到达本端时的网络波动 | 持续较高，并伴随音频断续或视频卡顿 |
| 丢包 | 最近一个采样周期的接收丢包比例 | 持续升高，并伴随听感或观感下降 |
| 画面 | 实际接收并解码的视频尺寸 | 长期低于预期，或显示为 0x0 |
| FPS | 实际接收或解码帧率 | 视频应播放但持续偏低或为 0 |
| 解码耗时 | 平均解码一帧所需时间 | 持续升高并伴随低 FPS、丢帧或卡顿 |

## 4. 网络连接

```text
状态:connected | ICE:connected | DTLS:connected
↑:320.0kbps/可用1.5Mbps | ↓:480.0kbps/可用-
```

| 页面字段 | 正常表现 | 异常时优先检查 |
| --- | --- | --- |
| 状态 | 通话稳定后通常为 `connected` | `disconnected` 持续不恢复，或进入 `failed` / `closed` |
| ICE | 通常为 `connected` 或 `completed` | 长期 `checking`、进入 `failed`：检查网络、NAT、防火墙和 TURN |
| DTLS | 通常为 `connected` | 长期 `connecting` 或进入 `failed`：媒体安全连接未建立 |
| `↑ 实际/可用` | 实际发送码率不超过当前可用上行带宽 | 可用带宽持续过低，同时出现上行画质下降或带宽受限 |
| `↓ 实际/可用` | 有下行媒体时存在实际接收码率 | 远端正在发送，但实际接收码率长期为 0 |

部分浏览器不提供可用下行带宽，因此 `↓` 后的“可用”显示 `-` 并不表示故障。

## 5. 网络质量

```text
RTT:34ms | ↑:极佳(1) | ↓:极佳(1)
```

RTT 是媒体数据往返时延。SDK 优先采用更接近当前媒体体验的 RTT；多路媒体同时存在时按最差一路判读。

上下行网络质量范围为 0～6，数字越大表示当前网络体验越差：

| 等级 | 含义 |
| ---: | --- |
| 0 | 暂无足够数据 |
| 1 | 极佳 |
| 2 | 较好 |
| 3 | 一般 |
| 4 | 差 |
| 5 | 极差 |
| 6 | 已断开或当前网络极差 |

等级反映当前采样，不是整通通话的平均值。短暂波动可以继续观察；连续多次处于 4～6，并且用户体验变差时，应按网络故障处理。

## 6. 存在问题

“存在问题”显示 SDK 根据当前报告识别到的主要风险，例如：

| 页面提示 | 通常含义 | 建议动作 |
| --- | --- | --- |
| 连接不可用 / 下行传输停滞 | 媒体连接不可用或长时间未收到数据 | 检查连接状态、远端发送状态、防火墙及 TURN |
| 高延迟 / 上行丢包 / 下行丢包 / 下行高抖动 | 当前网络质量影响媒体传输 | 更换稳定网络，检查弱网、跨网和出口拥塞 |
| 上行带宽受限 / 上行可用带宽不足 | 浏览器估算的上行能力不足以维持目标质量 | 降低分辨率、帧率或码率，检查上行带宽 |
| 编码器 CPU 受限 / 编码器过慢 | 本机编码性能不足 | 关闭高负载程序，降低视频规格，检查媒体特效开销 |
| 编码帧率下降 / 编码分辨率下降 | 实际发送质量低于采集源 | 结合带宽、CPU、码率和用户画面判断原因 |
| 解码器过慢 / 视频丢帧 / 视频卡顿 / 视频暂停 | 本机接收或渲染不顺畅 | 检查 CPU/GPU、浏览器负载、下行网络和远端发送状态 |
| 上下行重传请求多 | 近期网络丢包导致较多恢复请求 | 结合丢包、抖动、RTT 和用户体验继续排查 |
| 网络路径变化 | ICE 使用的网络路径发生变化 | 单次变化可观察；频繁出现时检查网络切换或不稳定 |

`L1`～`L6` 表示问题严重程度，数字越大越严重。“无”只表示当前报告没有达到内置诊断条件，不代表整通通话一定没有问题。

## 7. 按用户现象排查

| 用户现象 | 优先查看 |
| --- | --- |
| 音频断续、机器人音 | 音频上下行丢包、抖动、RTT、网络质量、下行缓冲或停滞提示 |
| 视频模糊、马赛克 | 上行视频码率、画面尺寸、可用带宽、限制原因、丢包 |
| 视频卡顿、低帧率 | 上下行 FPS、丢包、抖动、编码/解码耗时、CPU 限制、丢帧和卡顿提示 |
| 有信令但无媒体 | 状态、ICE、DTLS、对应 RTP 行、上下行实际码率、远端是否实际发送 |
| 切换设备或共享后短暂波动 | 先等待数个采样周期；持续不恢复时再按对应链路排查 |
